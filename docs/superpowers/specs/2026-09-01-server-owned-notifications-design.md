# TAPHOA Chat — Minimal Server-Owned Notifications

Date: 2026-09-01
Status: Approved in chat; written spec pending final user review
Scope: User ↔ Admin only
Next milestone after this feature: `user 1234`

## 1. Goal

Make notifications more reliable and harder to misroute while keeping the application small.

The core change is ownership:

- Chat/Call creation remains exactly where it is today.
- Once a message or call is successfully persisted on the server, the **backend** owns notification dispatch.
- The sender browser is no longer responsible for guaranteeing push delivery.
- Push delivery must prove the exact current relationship `profile -> device -> auth session -> push subscription` before sending.

This feature intentionally does **not** add Firebase, APNs, Redis, a generic worker queue, multiple notification providers, Rocket.Chat-style room rules, or Chatwoot-style notification settings complexity.

## 2. Product behavior

Keep only one user-facing notification control:

- `Bật thông báo` when permission/subscription is not ready.
- `Kiểm tra thông báo ✓` when the exact current device/session is registered and test delivery succeeds.

Do not add separate switches for Chat, Call, sound, mentions, rooms, or categories.

### 2.1 Chat

- If the recipient is currently viewing the exact conversation, do not show a system notification. Realtime updates the message in place.
- If the app is visible but the recipient is elsewhere in the app, show one concise system notification.
- If the app is backgrounded, closed, or the device is locked, show a system push notification.
- Tapping a Chat notification opens/focuses the correct User/Admin PWA and routes to the relevant conversation where the current UI can resolve it.
- No duplicate foreground notification mechanism is added.

### 2.2 Call

- If the app is visible, the Call UI is the notification: full/compact/hidden call presentation plus foreground ringtone/vibration.
- Do not show a second incoming-call system notification on top of a visible Call UI.
- If the app is backgrounded, closed, or locked, use Web Push.
- Accept/Decline stops foreground ringtone/vibration immediately.
- Existing PWA constraints remain. This design does not attempt to implement native iOS PushKit/CallKit behavior.

## 3. Approaches considered

### A. Keep client-owned push and add retries

Smallest code change, but it preserves the wrong owner. A message/call may already be committed while the sender page is suspended or closed before its fire-and-forget push request completes.

Rejected.

### B. Database-owned event + `pg_net` dispatch to the existing Edge Function

Use the database transaction as the source of truth, create a minimal private notification outbox event, and let Postgres `pg_net` call the existing `taphoaxyz-call-push` function after commit.

The Edge Function remains the single Web Push sender.

Chosen.

### C. Full queue/worker/FCM architecture

Reliable at large scale but adds services, operations and failure modes that are unnecessary for User ↔ Admin.

Rejected.

## 4. Server-owned notification flow

### 4.1 Current Chat flow

`client -> chat_send_text_message RPC -> message persisted -> sender client fire-and-forget Edge Function -> Web Push`

### 4.2 New Chat flow

`client -> chat_send_text_message RPC -> message persisted + notification event persisted -> commit -> pg_net -> existing Edge Function -> validated recipient sessions/subscriptions -> Web Push`

### 4.3 Current Call flow

`client -> chat_start_voice_call RPC -> call persisted -> sender client fire-and-forget Edge Function -> Web Push`

### 4.4 New Call flow

`client -> chat_start_voice_call RPC -> ringing call persisted + notification event persisted -> commit -> pg_net -> existing Edge Function -> validated recipient sessions/subscriptions -> Web Push`

Busy/rejected call-start results must never create a notification event.

Use one private SQL helper, `chat_private.notification_dispatch_url()`, as the single owner of the current Edge Function URL. Do not duplicate the project URL across message/call SQL code. The helper returns the current production function endpoint for `taphoaxyz-call-push`; moving Supabase projects later requires one configuration change, not rewrites throughout the schema.

## 5. Minimal notification outbox

Add one private/server-only table, for example `chat_notification_outbox`, with only the fields needed for ownership, idempotency and diagnostics:

- `id uuid primary key`
- `event_type` = `chat_message | incoming_call`
- `source_id uuid`
- `recipient_profile_id uuid`
- `dispatch_token uuid` generated by the database
- `created_at`
- `processed_at nullable`
- `last_error nullable`

Add a unique constraint on `(event_type, source_id, recipient_profile_id)` so an idempotent message send or repeated call path cannot enqueue duplicate notifications.

The table is not readable/writable by normal clients. Only SECURITY DEFINER database code and the service-role Edge Function use it.

### Why a per-event dispatch token

Do not add a permanent shared secret between Postgres and the Edge Function.

For each outbox row, Postgres generates a random one-time `dispatch_token` and sends only `{ event_id, dispatch_token }` through `pg_net`.

The Edge Function can dispatch only when both values match a private outbox row whose `processed_at` is null. Once processing is completed, `processed_at` is set and the same capability cannot dispatch again.

If the function dies before finishing the event, the row remains unprocessed and can be diagnosed or retried manually. This release deliberately does not add an automatic retry worker.

This keeps the architecture small and prevents a public caller from replaying arbitrary message/call IDs to generate notifications.

## 6. Exact account/session/device binding

This is a release-blocking security/correctness requirement.

Current subscriptions already have unique `device_id` and unique `endpoint`. Keep those guarantees.

Add `auth_session_id` to `chat_call_push_subscriptions` and bind every subscription to:

`profile_id + device_id + auth_session_id + endpoint`

### 6.1 Registration contract

`chat_upsert_call_push_subscription` must:

1. Resolve the authenticated current profile and current Supabase auth session.
2. Prove the supplied device belongs to that profile **through that exact current session**.
3. Rebind the endpoint atomically to the current owner if the browser reused a cached PushSubscription from an older account/session.
4. Store the current `auth_session_id` with the subscription.

Because `endpoint` is globally unique, a cached endpoint cannot remain owned by two accounts at once.

If the same browser endpoint appears under a new account/session, the new authenticated binding removes/replaces the stale old ownership before the new row becomes active.

### 6.2 Delivery contract

Do not let the Edge Function assemble this validity check from several public-table queries. Add one service-role-only SECURITY DEFINER RPC, for example `chat_service_push_targets(profile_id, optional_device_id)`, as the single owner of target validation.

That RPC may read `auth.sessions` and returns a push target only if all of these are true:

- subscription.profile_id = requested recipient profile
- subscription.device_id belongs to that same profile
- device.revoked_at is null
- subscription.auth_session_id matches a `chat_sessions` row for the same profile/device
- chat_sessions.revoked_at is null
- the same `auth_session_id` still exists in Supabase `auth.sessions`
- `auth.sessions.user_id` matches the profile's `auth_user_id`
- `auth.sessions.not_after` is null or still in the future

The RPC is not executable by `anon` or normal `authenticated` clients; only the server path may call it.

If any check fails, do **not** send to that endpoint.

Stale subscription rows may be removed opportunistically after they fail validation.

### 6.3 What this prevents

- notification sent to an account that previously used the same browser/device
- notification sent through an old cached Supabase session
- notification sent after current session revoke/sign-out
- notification sent after Supabase auth session removal/expiry
- one Push endpoint remaining attached to both User and Admin identities
- stale local cache being treated as authorization

The push endpoint is transport data, never identity proof.

## 7. Edge Function responsibilities

Keep one function: `taphoaxyz-call-push`.

Existing authenticated actions remain:

- `config`
- `test`

Add one server-owned internal action:

- `dispatch_event`

`dispatch_event` receives only the outbox event ID and its one-time dispatch token.

The function then:

1. Validates the pending outbox event with service-role access.
2. Loads the canonical message/call from the database.
3. Re-validates that the recipient in the outbox still matches the canonical conversation/call.
4. Calls the service-only push-target RPC to obtain only exact valid sessions/subscriptions.
5. Sends Web Push.
6. Deletes expired 404/410 endpoints as today.
7. Sets `processed_at` when the attempt finishes and records `last_error` when delivery has an error.

Do not trust notification title/body/recipient sent over HTTP from Postgres. Build payloads from canonical database data inside the Edge Function.

## 8. Client changes

After server dispatch is verified:

- remove `sendChatMessagePush(...)` from the sender-side `message-backend.ts` success path
- remove `sendIncomingCallPush(...)` from `VoiceCallSession.startOutgoing()`
- keep notification registration/self-test on the client because permission and PushManager are device/browser responsibilities
- keep foreground Call alert controller because ringtone/vibration while the app is visible is a UI/runtime responsibility

The client sends Chat/Call; the server decides notification delivery.

## 9. Foreground suppression

Incoming Call already has the correct principle: if a visible app window is handling the call, do not show a duplicate system Call notification.

For Chat, the Service Worker needs only enough current UI context to answer one question:

`Is a visible app window currently displaying this conversation_id?`

Do not persist a new notification context cache. At push time the Service Worker:

1. gets visible window clients;
2. sends a small `CHAT_NOTIFICATION_CONTEXT_QUERY` with the incoming `conversation_id` through `MessageChannel`;
3. each visible page replies whether that exact conversation is currently selected;
4. if any visible page replies `true`, suppress the system Chat notification;
5. if visible pages reply `false`, show one system Chat notification;
6. if there is no answer within a short bounded timeout, default to showing the notification.

This adds no notification-preference store and avoids making cached UI state an authority.

## 10. Failure behavior

Notification failure must never roll back or falsely fail the already-created message/call.

- Chat persistence success remains success even if push delivery later fails.
- Call creation success remains success even if push delivery later fails.
- `last_error` provides enough evidence for diagnostics.
- No generic retry worker is introduced in this release.
- If production evidence later shows transient server-dispatch failures are common, a tiny retry policy can be added as a separate change rather than pre-building a queue system now.

## 11. Migration safety

For existing push subscriptions:

1. Backfill `auth_session_id` only when there is exactly one valid current session for the same profile/device.
2. Remove subscription rows that cannot be safely matched to a non-revoked current chat session and a live Supabase `auth.sessions` row.
3. Then enforce the new session binding.

Losing a stale push registration is safer than guessing its owner. The user can restore it with the existing `Bật thông báo / Kiểm tra thông báo ✓` flow.

No message, call, profile, or conversation business data is deleted.

## 12. Tests / release gates

Required automated gates:

- Chat RPC creates exactly one outbox event for a newly persisted direct User ↔ Admin text message.
- Idempotent re-send of the same client message ID does not create duplicate outbox events.
- Successful Call start creates exactly one incoming-call outbox event.
- Busy/rejected Call start creates none.
- Client Chat send path no longer invokes push directly.
- Client outgoing Call path no longer invokes push directly.
- Subscription upsert binds current profile + device + auth session.
- Cached endpoint rebind removes stale previous ownership.
- Revoked chat session cannot receive push.
- Missing/expired Supabase `auth.sessions` session cannot receive push.
- Revoked device cannot receive push.
- Active exact session/device can receive push.
- Exact-device self-test still works and is limited to the current session/device owner.
- 404/410 subscriptions are still cleaned.
- Visible incoming Call does not create duplicate system notification.
- Visible exact Chat conversation suppresses its system notification.
- Visible different Chat conversation still receives one concise system notification.
- Service Worker probe timeout fails open to one system notification rather than silently dropping it.
- Full TypeScript/test/build regression passes.
- Physical iPhone PWA + Android test verifies no cross-account/session notification after logout/account switch.

## 13. Explicit non-goals

- Firebase/FCM migration
- APNs/PushKit/CallKit
- notification center/history screen
- multiple notification categories or per-room settings
- mention rules
- mute schedules / quiet hours
- generic job queue
- analytics/dashboard for push
- groups/conferences

## 14. Completion condition

This notification milestone is complete only when:

1. server owns Chat and Call push dispatch;
2. no sender client fire-and-forget push remains in the production flow;
3. every push target is validated against exact current profile/device/auth session and live Supabase auth session;
4. cached/stale endpoint ownership cannot produce cross-account notification;
5. foreground suppression behaves without duplicate/lost notifications;
6. User/Admin physical-device regression passes.

After this milestone is complete, the next requested work item is **`user 1234`**.
