# Zalo User Link Bridge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Admin optionally link one existing TAPHOA Chat User to one Zalo personal-contact identity so only new typed text after `linked_at` flows between that existing Chat conversation and Zalo, without creating a second chat system.

**Architecture:** Keep `v21_accounts`, `v21_conversations`, `v21_messages`, SyncEngine, Composer, media, Call, and the sidebar as the canonical Chat system. Add an additive Supabase bridge schema plus service-role-only ingress/outbound RPCs, a dedicated Admin API/UI for linking, and an isolated Render worker under `bridge/zalo/`. The worker talks to Zalo only through a small adapter; Phase 1 uses `zca-js@2.2.0` behind that adapter and unit tests always use a fake adapter.

**Tech Stack:** Static HTML/JS PWA, Supabase Postgres/RPC/Edge Functions, Node.js 20+, built-in `node:test`, `@supabase/supabase-js`, `zca-js@2.2.0`, Render Web Service.

**Spec:** `docs/superpowers/specs/2026-09-11-zalo-user-link-bridge-design.md`

## Global Constraints

- Base implementation from `main` SHA `0694ea12ba4af9c51049e9f83b740c7b111ed052`; rebase/refresh before execution if `main` moves.
- Admin-only link management; target must be an existing `v21_accounts.role='user'` account.
- One Chat User ↔ one Zalo identity; unlink deletes the active mapping and releases that Zalo identity.
- No import of old Zalo history and no export of old Chat history; `linked_at` is the hard boundary.
- Phase 1 transports non-empty typed body text only. Chat media remains fully functional but is not sent to Zalo.
- Unlinked Users create zero bridge work and must behave exactly as before.
- Browser never receives Zalo credentials or service-role credentials and never writes bridge tables directly.
- Canonical Chat messages remain in `v21_messages`; do not create a parallel UI message store.
- The current `v21_messages_emit_sync_trg` remains responsible for SyncEngine/Realtime delivery after inbound canonical message insert.
- `zca-js` is unofficial and can expose a personal Zalo account to lock/ban risk; keep it isolated behind `ZaloAdapter`, never call real Zalo from CI, and document that only one Zalo Web listener can be active for the account.
- Existing `python tools/verify_current.py` must stay green. Merge only after exact-feature-SHA verification and post-migration smoke checks.

`v21_zalo_admin_link` must verify actor role `admin`, target role `user`, target not deleted, Zalo exists, then `delete from zalo_user_links where chat_account_id=p_target_account_id` followed by `insert`. A uniqueness conflict on `zalo_id` must roll back the delete automatically and surface `zalo_already_linked`.

`v21_zalo_ingress` must:

```sql
-- pseudocode contract inside the SECURITY DEFINER function
select * into v_link from public.zalo_user_links where zalo_id=p_zalo_id;
if not found or p_event_at < v_link.linked_at then return null; end if;
-- linked_by_account_id is the Admin-side conversation owner.
-- create canonical admin/user conversation pair if absent.
-- client_id := 'zalo:' || left(p_zalo_id,40) || ':' || left(p_zalo_message_id,72)
-- insert v21_messages with sender_account_id = chat_account_id and created_at = p_event_at.
-- on sender/client_id conflict return existing message id.
-- insert inbound zalo_message_links with state='received' on conflict do nothing.
```

`v21_private.enqueue_zalo_outbound()` must only queue rows when:

```sql
new.body <> ''
AND sender role = 'admin'
AND the opposite conversation member is role='user'
AND that User has a current zalo_user_links row linked by this Admin
AND new.created_at >= linked_at
```

`v21_zalo_outbound_due(20)` returns due `pending` rows plus `failed` rows with `attempt_count < 5` after bounded delay `least(300, 5 * power(2,attempt_count))` seconds, joined to `v21_messages.body`.

`v21_zalo_outbound_result` sets `sent + zalo_message_id` on success; on failure increments `attempt_count`, stores a bounded error string, and sets `failed`.

- [ ] **Step 3: Implement `createBridge` with no Zalo-specific imports**

```js
export function createBridge({adapter,gateway,logger=console}){
  let started=false, polling=false;
  const onMessage=async event=>{
    if(!event?.zaloId||!event?.messageId||!String(event?.text||'').trim())return;
    if(event.profile)await gateway.upsertContact(event.profile);
    await gateway.ingestText(event);
  };
  return {
    async start(){ if(started)return; started=true; await adapter.start(onMessage); },
    async pollOutbound(){
      if(!started||polling)return 0;
      polling=true;
      try{
        const rows=await gateway.listOutbound(20);
        for(const row of rows){
          try{
            const external=await adapter.sendText({zaloId:row.zaloId,text:row.text});
            await gateway.markOutboundResult({deliveryId:row.deliveryId,ok:true,zaloMessageId:external?.messageId||null});
          }catch(error){
            await gateway.markOutboundResult({deliveryId:row.deliveryId,ok:false,error:String(error?.message||error)});
          }
        }
        return rows.length;
      }finally{polling=false;}
    },
    async stop(){ if(!started)return; started=false; await adapter.stop(); }
  };
}
```
